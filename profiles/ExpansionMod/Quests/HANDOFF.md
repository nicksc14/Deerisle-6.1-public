## 10. JSON 编辑不变量

1. 修改前完整读取目标 Quest 与其所有 Objective、NPC、前置/后继任务；不能只改搜索命中的单行。
2. 保持当前 schema 和 `ConfigVersion`。除非 Expansion 升级要求迁移，不得自行增删必要字段。
3. 严格保留原文件缩进、字段顺序和未涉及行；不要用会重排整个 JSON 的序列化工具覆盖文件。
4. Quest 中每个 `{ "ID", "ObjectiveType" }` 必须有匹配的 Objective 文件。Objective ID 只在类型范围内解释；`1211` 复用 `Travel 1202` 是有意设计。
5. `PreQuestIDs` 中列出的任务按当前链路均为必要前置。修改前置时要同时检查是否造成死链、提前解锁或 `MaxActiveQuests` 冲突。
6. `SequentialObjectives=1` 时，Objective 按数组顺序推进。Travel 后击杀/寻宝的任务不得随意调换顺序。
7. `Descriptions` 的 0/1/2 分别对应接取、进行中、完成阶段；三段都要与标题、目标、奖励和服务器机制一致。
8. Reward 每一项的必要字段必须完整保留，包括 `ClassName`、`Amount`、`Attachments`、`DamagePercent`、`HealthPercent`、`QuestID`、`Chance`。即使值为空数组或默认值也不能擅删。
9. Collection/Delivery 修改时联合检查 `PlayerNeedQuestItems`、`DeleteQuestItems`、数量与最低剩余百分比，避免重复利用或无法交付。
10. Treasure Loot 项的 `Name`、`Chance`、`Attachments`、`QuantityPercent`、`Max`、`Min`、`Variants` 均须保留；`LootItemsAmount` 必须与期望生成总量匹配。
11. 坐标统一按 `[x,y,z]`；Travel/Target 半径、AIWarZone 或 MPG 触发区必须几何重合。
12. 新奖励 classname 必须在当前服务器加载的原版/模组配置中存在；枪、弹匣、附件必须验证兼容，不能凭名称推断。

## 11. 数量、耐久和食物药品规则

- Quest Reward 的 `Amount` 表示生成数量/单位，最终形态还受该物品 classname 的堆叠上限与 Expansion 生成逻辑影响。
- 弹药先查 CDS 自定义 `count`。例如当前 `Ammo_556x45` 上限 200，发放 120 有效；如果未来 CDS 改为更小堆叠，必须重新验证是否分堆、截断或生成失败。
- 可消耗品、药品、食物和容器不能只看 `Amount`；还要检查 `QuantityPercent`、Objective 的 `MinQuantityPercent`、健康/损伤百分比以及物品自身 energy/liquid/数量语义。
- `QuantityPercent`、`Min`、`Max` 在 Treasure 中不是可省略的装饰字段。修改宝箱数量时应做最小值、最大值和总生成数量的边界测试。
- 任务文本若要求“完整”“至少一半”“若干次使用量”，必须与 JSON 的最低数量/剩余量条件完全一致。
